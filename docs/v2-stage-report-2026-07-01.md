# HeatedTopics v2 阶段报告

生成时间：2026-07-01

## 1. 项目定位

HeatedTopics v2 是在原有 DailyHot 热榜采集之外新增的一条“主动搜索发现”链路。v1 更像是从已有热榜里挑选话题，v2 则从创作者画像出发，主动生成搜索关键词，调用多个搜索 API，汇总候选内容，再输出给用户和大语言模型使用的结构化选题信息。

当前 v2 的核心目标是：

- 根据用户画像和内容方向生成检索 query。
- 自动选择适合的搜索源。
- 将不同搜索源返回的数据标准化。
- 汇总为候选话题、证据、统计结果和 Markdown 报告。
- 在可配置大语言模型时，进一步做归纳、总结和建议。

## 2. 前期调研和设计结论

前期调研主要围绕三件事展开。

第一，搜索源选择。项目最初评估了 GitHub、百度千帆、博查、阿里百炼、Tavily、天聚数行、七牛等搜索或内容检索接口。不同源的适用场景不同：GitHub 适合开源项目和技术工具，千帆和七牛偏国内网页，博查和天聚偏新闻事实，Tavily 适合全球网页和英文摘要。

第二，画像驱动路由。v2 不使用固定 query，而是根据创作者画像里的 `role`、`profile_type`、`track_tags`、`custom_keywords`、`content_modes` 和 `content_goal` 判断搜索意图，再为不同 source 生成不同 query。这样比“一组关键词搜所有平台”更容易得到可解释结果。

第三，输出约束。设计上要求 LLM 只能基于真实搜索结果做总结，不能补充无来源事实；搜索失败、缺 key、鉴权失败都要进入原始数据，便于排查，但不能混入最终有效话题。

## 3. 当前已完成内容

### 3.1 搜索发现主流程

当前已经形成完整链路：

```text
CreatorProfile
  -> Intent / Route
  -> Per-source Query
  -> Search Providers
  -> Normalized Results
  -> Evidence
  -> Topic Index
  -> Analysis JSON / Markdown Report
```

主要产物包括：

- `data/search_discovery/raw/search_results.jsonl`
- `data/search_discovery/evidence/search_content_evidence.jsonl`
- `data/search_discovery/processed/search_topic_index.json`
- `data/search_discovery/processed/topic_analysis.json`
- `reports/search_discovery/search_topic_recommendations.md`
- `reports/search_discovery/topic_analysis.md`

### 3.2 API 配置和连通性测试

已经实现 `src.search_discovery.config_api` 配置助手，支持：

- 查看当前 source 配置状态。
- 单独配置某个 source。
- 配置后立即测试。
- 跳过测试以节省 API。
- 冒烟测试 `--smoke-test`，每个已配置 source 只调用一次，并尽量只返回 1 条结果。

这解决了早期“key 配错但不知道哪里错”的问题。

### 3.3 百度千帆新版接口适配

已经将 `baidu_qianfan_search` 适配到千帆新版 API Key 方式。新版 `bce-v3/ALTAK...` 形式的 key 只需要配置 `QIANFAN_API_KEY`，不再强制要求 `QIANFAN_SECRET_KEY`。

旧版 `API Key + Secret Key` 仍保留兼容逻辑。

### 3.4 大语言模型归纳能力

已经接入 OpenAI-compatible Chat 调用，并对 MiniMax 做了适配：

- `MINIMAX_API_KEY`
- `MINIMAX_BASE_URL`
- `MINIMAX_MODEL`

当 `--analysis-mode model` 开启时，系统会尝试调用模型生成整体归纳和逐话题建议。模型调用失败时，不中断流程，会退回规则归纳，并在 `topic_analysis.json` 里记录 `model_error`。

当前财经样例中 MiniMax 返回了 `HTTP Error 401: Unauthorized`，说明模型鉴权还没有成功，需要进一步检查 MiniMax key、base url 或模型权限。

### 3.5 搜索引擎来源标记

搜索结果中已经新增 `search_engine` 字段，报告中也能显示每条证据来自哪个搜索引擎，例如：

- `Baidu Qianfan Search`
- `Tavily Search`
- `TianAPI News`
- `Bocha AI Search`
- `Qiniu Web Search`

这对后续评估“哪类 source 对哪类话题更准”很关键。

## 4. 当前检索匹配准确度评估

基于最近一次财经/股票样例，当前匹配准确度可以判断为：领域相关性基本可用，但选题可用性和精确匹配仍然偏弱。

### 4.1 表现较好的部分

前 10 条百度千帆结果大多能命中财经、股票、A股、港股、美股等关键词。比如东方财富行情中心、同花顺港股页面、美股新闻页等，方向上是对的，说明画像关键词确实能把检索范围拉到财经股票领域。

搜索源来源也已经可见，便于判断结果来自国内网页还是全球网页。对用户来说，报告已经不是黑盒列表，而是能追溯到具体搜索引擎和 URL。

### 4.2 表现不足的部分

第一，结果偏“入口页”和“频道页”。例如“财经首页”“美股”“新闻”“全球”这类标题虽然相关，但不一定是一个明确选题。它们适合作为线索入口，不适合作为最终内容标题。

第二，Tavily 返回的英文财经新闻和市场信息整体相关，但 `matched_keywords` 出现为空。这说明当前关键词匹配更偏中文字符串直接命中，对英文结果、同义词、实体词、证券代码和跨语言匹配支持不足。

第三，本次没有多源交叉命中。20 个话题里没有一个同时被两个搜索源支持，这会导致可信度和排序稳定性不足。财经内容尤其需要交叉验证，单一来源不适合直接进入发布级结论。

第四，搜索源覆盖不完整。TianAPI、Bocha、Qiniu 因 key 缺失没有贡献有效结果，导致国内新闻源和通用搜索补充不足。财经场景下，这会显著影响时效新闻、公告、政策解读类话题的召回。

第五，当前评分更多是启发式规则，不是经过人工标注集验证的准确率。现有分数能表达“来源权重、关键词命中、详情程度、时效性、风险”的综合判断，但还不能等同于真实点击率、可写性或事实可靠性。

### 4.3 粗略准确度判断

如果只看“是否属于财经/股票大方向”，本次结果大致是可用的，约多数结果都在财经、股票、市场或上市公司范围内。

如果看“是否能直接成为一个清晰选题”，准确度明显下降。频道页、行情页、首页类结果需要二次拆解；英文市场新闻需要翻译、实体识别和事实核验；单源结果需要补证。

因此当前 v2 更适合定位为“选题线索发现器”，还不适合直接作为“高置信选题生产器”。

## 5. 当前不足

### 5.1 Query 生成仍偏粗

财经场景只使用 `A股 港股 美股 股票市场 上市公司财报` 这种宽泛 query，会召回大量门户首页、行情页和频道页。缺少更细的 query 维度，例如：

- 财报预告
- 业绩快报
- 回购
- 减持
- 新股上市
- 行业政策
- 大宗商品影响
- 美联储利率
- 港股 IPO

### 5.2 话题聚类粒度偏浅

当前聚类主要根据标题、URL、来源结果合并。对于同一市场事件，不同媒体可能标题差异很大，系统还不能稳定识别“这是同一个事件”。

### 5.3 缺少财经实体识别

财经内容高度依赖实体：

- 公司名
- 股票代码
- 指数名
- 行业板块
- 交易所
- 机构名
- 财报周期

当前系统还没有专门抽取这些实体，导致排序和去重很难判断“这是明确公司事件”还是“只是市场频道页”。

### 5.4 缺少人工标注评测集

目前准确度主要靠样例运行和人工观察，没有一套固定评测集。没有评测集，就很难量化改动到底让准确率提升还是下降。

### 5.5 大模型总结链路还未稳定

LLM 归纳能力已经接入，但 MiniMax 鉴权失败导致本次没有真实模型输出。规则归纳可以保底，但对复杂财经话题的提炼、风险提示和建议仍然不如模型归纳。

### 5.6 源代码里存在中文编码遗留风险

部分早期设计文本和少量代码注释或字符串在终端显示存在乱码痕迹。虽然当前主流程可以运行，但这会影响中文 intent 判断、query 模板维护和后续协作可读性，需要专门清理。

## 6. 后续提升方向

### 6.1 建立人工标注评测集

建议先固定 3-5 类画像，每类保存 20-50 条搜索结果，人工标注：

- 是否领域相关。
- 是否是明确事件。
- 是否适合创作。
- 是否需要补证。
- 风险等级是否合理。

然后用这些标注来计算：

- Top 5 准确率。
- Top 10 准确率。
- 可直接创作率。
- 单源误判率。
- 频道页误召回率。

这是后续优化最重要的地基。

### 6.2 财经 query 分层生成

不要只生成一条宽泛 query，而是按意图拆成多条小 query：

| 类型 | 示例 |
| --- | --- |
| 市场趋势 | `A股 今日 板块 资金流向` |
| 公司事件 | `上市公司 财报 业绩预告 净利润` |
| 政策影响 | `证监会 政策 A股 影响` |
| 港股美股 | `港股 IPO 财报`、`US stocks earnings guidance` |
| 风险提示 | `减持 暴雷 退市 风险提示` |

这样可以减少首页类结果，提高事件型结果比例。

### 6.3 增加结果类型过滤

对财经场景可以降低以下类型的排名：

- 纯行情首页。
- 频道首页。
- 没有发布时间的聚合页。
- 标题过短且摘要泛化的页面。

提高以下类型的排名：

- 带公司名或股票代码。
- 带明确时间。
- 带财报、公告、政策、交易、IPO、回购、减持等事件词。
- 多源共同提及。

### 6.4 做跨源事件合并

后续可以用“实体 + 时间 + 事件词”聚类。例如：

```text
公司名/股票代码 + 财报/回购/减持/IPO + 日期
```

只要多个来源命中同一组实体和事件，就合并为一个更高置信话题。这样可以显著提升报告里的可信度。

### 6.5 加入领域词典和跨语言匹配

财经方向至少需要维护：

- 中文财经关键词词典。
- 英文财经关键词词典。
- 常见同义词映射。
- 指数、交易所、行业板块词典。
- 股票代码和公司名映射。

这样 Tavily 的英文结果就不会因为没有直接命中中文关键词而被低估。

### 6.6 稳定 LLM 归纳链路

先修复 MiniMax 401 鉴权问题，然后让模型承担更适合它的工作：

- 判断一个结果是不是“可写选题”。
- 把频道页拆解成具体选题方向。
- 合并同一事件的多条证据。
- 输出面向用户的标题建议、角度建议、风险提示。
- 输出面向 LLM 的结构化上下文。

但模型不应该决定事实是否存在，事实仍必须来自搜索证据。

### 6.7 搜索源补齐和权重调优

财经方向建议优先补齐：

- 天聚数行：补国内新闻时间线。
- 博查：补中文综合新闻和网页摘要。
- 七牛：作为国内网页兜底。

补齐后再根据标注集调权重。比如财经类画像下，新闻源和公告源权重应高于通用网页源；技术类画像下，GitHub 和技术文章源权重应更高。

## 7. 建议下一阶段目标

下一阶段不建议继续盲目接更多 API，而应优先提升“准”和“稳”。

建议目标：

1. 修复 MiniMax 鉴权，跑通真实模型归纳。
2. 建立 50-100 条人工标注评测集。
3. 为财经场景实现 query 分层生成。
4. 加入频道页降权和事件词升权。
5. 增加财经实体抽取字段。
6. 做跨源事件合并，让多源命中成为高置信选题。
7. 形成一份“Top 10 可写选题报告”，而不是单纯搜索结果列表。

## 8. 阶段结论

v2 当前已经完成从画像、搜索、证据、话题、统计、报告到模型归纳接口的主链路搭建，具备端到端运行能力。它已经能把用户方向转成搜索任务，并输出可追溯的数据和报告。

但当前质量还处在“可发现线索”的阶段，离“稳定产出高质量选题”还有距离。主要差距不是工程链路，而是检索策略、领域理解、跨源验证和评测体系。

短期内最值得投入的是财经场景专项优化：拆 query、识别实体、过滤频道页、提高多源交叉命中，再用人工标注集验证效果。做到这一步后，v2 才能从工具型搜索流程，升级成真正可靠的选题发现系统。
