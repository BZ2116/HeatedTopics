# Search Topic Analysis Design

## Purpose

The v2 search discovery pipeline can already collect search results, enrich them into evidence, cluster candidate topics, and render a recommendation report. The next step is to add an analysis layer that organizes, summarizes, and measures those collected topics for two different consumers:

1. Human users who need a readable topic analysis report with judgment, evidence, and content suggestions.
2. Large language models and downstream automation that need structured statistics and compact topic context.

The design uses deterministic rule analysis as the baseline and optional model synthesis as an enhancement. A normal run must still produce useful output without a model API key.

## Current Flow

Existing v2 outputs are generated by `src/search_discovery/cli.py`:

```text
provider rows
  -> SearchResult[]
  -> EnrichedContent[]
  -> CandidateTopic[]
  -> data/search_discovery/raw/search_results.jsonl
  -> data/search_discovery/evidence/search_content_evidence.jsonl
  -> data/search_discovery/processed/search_topic_index.json
  -> reports/search_discovery/search_topic_recommendations.md
```

The analysis layer should run after `CandidateTopic[]`, `SearchResult[]`, and `EnrichedContent[]` are available. It should not change provider fetching, route planning, or the existing topic index schema.

## Goals

- Produce a human-facing Markdown analysis report with clear recommendations.
- Produce a machine-facing JSON artifact with statistics, per-topic features, evidence, and model-ready context.
- Support optional LLM synthesis for overall conclusions and per-topic suggestions.
- Keep rule output deterministic and testable.
- Fail soft when model synthesis is unavailable or returns invalid data.
- Reuse the existing OpenAI-compatible model calling style from `src/core_pipeline/model_topic_summarizer.py`.

## Non-Goals

- Do not replace the existing `search_topic_recommendations.md` report in this change.
- Do not fetch full page bodies beyond the existing `EnrichedContent` layer.
- Do not make model calls mandatory for the v2 pipeline.
- Do not add a dashboard UI yet.
- Do not automatically generate full scripts or articles in this layer.

## User Experience

Rule-only analysis:

```powershell
uv run python -m src.search_discovery.cli `
  --profile config/search_discovery/creator_profiles/tech_ai_creator.json `
  --render-analysis `
  --analysis-mode rule
```

Model-enhanced analysis:

```powershell
uv run python -m src.search_discovery.cli `
  --profile config/search_discovery/creator_profiles/tech_ai_creator.json `
  --render-analysis `
  --analysis-mode model
```

The default `analysis-mode` is `rule`. When `--render-analysis` is not passed, the existing search discovery behavior is unchanged.

Model configuration should follow the existing OpenAI-compatible convention:

```text
OPENAI_API_KEY=
OPENAI_BASE_URL=
OPENAI_MODEL=
```

If `OPENAI_MODEL` is absent, the code should use the same default model constant used by the existing core pipeline model summarizer unless the implementation later introduces a dedicated search-discovery default.

## Output Files

Add two new outputs:

| Path | Consumer | Description |
| --- | --- | --- |
| `data/search_discovery/processed/topic_analysis.json` | Programs and LLMs | Structured statistics, topic features, evidence, rule summaries, compact LLM context, and optional model synthesis. |
| `reports/search_discovery/topic_analysis.md` | Human users | Readable analysis report with overview, recommended topics, evidence, creator angles, and verification notes. |

These outputs are generated only when `--render-analysis` is passed.

## JSON Shape

`topic_analysis.json` should use this top-level shape:

```json
{
  "schema_version": "0.1",
  "generated_at": "2026-06-30T16:26:40+08:00",
  "profile": "config/search_discovery/creator_profiles/tech_ai_creator.json",
  "statistics": {
    "total_topics": 30,
    "total_results": 32,
    "total_evidence": 32,
    "source_distribution": {},
    "keyword_distribution": {},
    "risk_distribution": {},
    "content_type_distribution": {},
    "freshness_distribution": {},
    "score_buckets": {},
    "recently_recommended_count": 0
  },
  "topics": [],
  "model_synthesis": null,
  "model_error": null
}
```

Each item in `topics` should include:

```json
{
  "topic_id": "search_topic_001",
  "title": "Topic title",
  "priority": "high",
  "topic_score": 73,
  "matched_keywords": ["AI Agent"],
  "keyword_categories": ["tech_project"],
  "freshness": "breaking",
  "risk_level": "low",
  "detail_level": "high",
  "evidence_count": 2,
  "source_ids": ["github_search", "baidu_qianfan_search"],
  "content_types": ["repo", "web"],
  "rule_summary": {
    "one_line_summary": "",
    "why_it_matters": "",
    "creator_angles": [],
    "recommended_format": "",
    "verification_notes": []
  },
  "evidence": [],
  "llm_context": {
    "compact_summary": "",
    "evidence_bullets": [],
    "source_titles": [],
    "metrics": {},
    "risk_flags": []
  }
}
```

Priority should be deterministic:

| Priority | Rule |
| --- | --- |
| `high` | `topic_score >= 70` |
| `medium` | `topic_score >= 50` and `< 70` |
| `low` | `topic_score < 50` |

Score buckets should be deterministic:

| Bucket | Rule |
| --- | --- |
| `80_plus` | `topic_score >= 80` |
| `60_to_79` | `topic_score >= 60` and `< 80` |
| `40_to_59` | `topic_score >= 40` and `< 60` |
| `under_40` | `topic_score < 40` |

## Model Synthesis Shape

When `analysis-mode=model`, the model should return a fixed JSON object:

```json
{
  "overall_summary": {
    "core_conclusion": "",
    "topic_landscape": "",
    "creator_strategy": "",
    "risk_and_verification": ""
  },
  "topic_suggestions": {
    "search_topic_001": {
      "one_line_summary": "",
      "why_it_matters": "",
      "creator_angles": [],
      "recommended_format": "",
      "verification_notes": []
    }
  }
}
```

The normalized `model_synthesis` stored in `topic_analysis.json` should add metadata:

```json
{
  "mode": "model",
  "model": "gpt-4.1-mini",
  "generated_at": "2026-06-30T16:26:40+08:00",
  "overall_summary": {},
  "topic_suggestions": {}
}
```

Model output must be treated as advisory text. It should not mutate deterministic statistics, topic scores, source IDs, or evidence counts.

## Markdown Report Shape

`topic_analysis.md` should be aimed at a creator or operator reading the result directly:

```text
# 选题分析报告

Generated at: `...`

## 本轮概览
统计总数、主要来源、关键词分布、风险概况。

## 归纳总结
优先使用 model_synthesis.overall_summary；没有模型结果时使用规则总结。

## Top 选题
按 priority 和 topic_score 排序展示前若干项。

## 话题详情
每个话题展示摘要、为什么值得做、创作角度、证据来源、风险和核验建议。

## 统计附录
来源、关键词、内容类型、风险、freshness、score bucket 的表格。
```

For per-topic prose, prefer model suggestions when present. Fall back to `rule_summary` otherwise.

## Components

### `analysis.py`

Responsibilities:

- Build statistics from `SearchResult[]`, `EnrichedContent[]`, and `CandidateTopic[]`.
- Convert each `CandidateTopic` into a structured analysis row.
- Generate rule summaries, creator angles, recommended formats, and verification notes.
- Build compact `llm_context` for optional model synthesis.

Public functions:

```python
def build_topic_analysis(
    *,
    profile_path: Path,
    generated_at: str,
    topics: list[CandidateTopic],
    results: list[SearchResult],
    evidence: list[EnrichedContent],
    model_synthesis: dict[str, Any] | None = None,
    model_error: dict[str, Any] | None = None,
) -> dict[str, Any]:
    ...
```

### `model_analysis.py`

Responsibilities:

- Compact the analysis payload before sending it to the model.
- Build a strict prompt requesting JSON only.
- Call an injected model function in tests, or the OpenAI-compatible chat helper in real runs.
- Normalize malformed or partial model output.
- Return either `model_synthesis` or `model_error`.

Public functions:

```python
def build_model_topic_analysis(
    *,
    analysis: dict[str, Any],
    model_call: Callable[[list[dict[str, str]]], dict[str, Any]],
    model: str,
    generated_at: str,
    max_topics: int = 12,
) -> dict[str, Any]:
    ...
```

### `analysis_render.py`

Responsibilities:

- Render `topic_analysis.json` into human-readable Markdown.
- Prefer model text where available.
- Fall back to rule summaries when model text is missing.
- Keep source links and verification notes visible.

Public functions:

```python
def render_topic_analysis_markdown(analysis: dict[str, Any]) -> str:
    ...
```

### `cli.py`

Add arguments:

```python
parser.add_argument("--render-analysis", action="store_true")
parser.add_argument("--analysis-mode", choices=("rule", "model"), default="rule")
```

Extend `_output_paths()` with:

```python
"topic_analysis": root / "data/search_discovery/processed/topic_analysis.json",
"analysis_report": root / "reports/search_discovery/topic_analysis.md",
```

When `--render-analysis` is set:

1. Build rule analysis.
2. If `analysis-mode=model`, call model synthesis using the compact analysis payload.
3. Rebuild or update analysis with `model_synthesis` or `model_error`.
4. Write `topic_analysis.json`.
5. Write `topic_analysis.md`.

## Rule Summary Heuristics

Rule summaries should be conservative and evidence-grounded:

- `one_line_summary`: use the existing `topic.summary` with light cleanup and truncation.
- `why_it_matters`: mention matched keywords, source diversity, freshness, and score.
- `creator_angles`: derive from keyword categories and content type:
  - `tech_project`: project teardown, tool comparison, implementation guide.
  - `tech_article`: tutorial summary, practice checklist, architecture explanation.
  - `news_trend`: timeline, impact analysis, follow-up watchlist.
  - `product_trend`: product comparison, use-case analysis, market interpretation.
  - fallback: trend observation and evidence roundup.
- `recommended_format`: choose from article, video, carousel, short post, or research note based on source type and risk.
- `verification_notes`: include risk warnings, single-source warnings, stale or missing date warnings, and recently recommended warnings.

## Error Handling

- Missing model credentials in `analysis-mode=model`: still write rule outputs and store `model_error` with type `missing_model_key`.
- Model call exception: still write rule outputs and store `model_error` with exception class and a short message.
- Non-JSON model output: still write rule outputs and store `model_error` with type `invalid_model_json`.
- Partial model JSON: normalize missing fields to empty strings or empty lists.
- Empty topic list: write statistics with zero counts and a Markdown report that says no usable topics were found.

## Testing Strategy

Add focused tests under `tests/search_discovery/`:

- `test_analysis.py`
  - statistics count sources, keywords, risks, content types, freshness, score buckets.
  - topic analysis rows include priority, evidence count, source IDs, rule summary, and `llm_context`.
  - empty inputs produce stable zero-count output.

- `test_model_analysis.py`
  - compact payload limits topic count and text size.
  - valid injected model output is normalized.
  - missing fields are normalized.
  - invalid model output returns a model error without raising.

- `test_analysis_render.py`
  - Markdown includes overview, top topics, model summary when present, rule fallback when absent, evidence links, and statistics appendix.

- CLI tests
  - `--render-analysis --analysis-mode rule` writes both analysis files.
  - `--render-analysis --analysis-mode model` uses injected model call in unit tests and writes `model_synthesis`.
  - model failure still writes files and returns a successful command result.
